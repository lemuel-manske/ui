# Agent access

Use these documents with the same library version installed in the consuming application.
Keep separate build artifacts for releases and check `agent/docs/version.json` in the portal
for version metadata.

## Live access through MCP

From the repository root, build the workspace dependencies, then start Storybook:

```sh
npm run build
npm run storybook
```

Configure your agent's MCP client with the HTTP endpoint `http://localhost:6006/mcp`.
Storybook must remain running and be reachable from the agent's environment.
Open that URL in a browser to inspect the available tools and manifest debugger.

Ask the agent to list documented components, retrieve the relevant APIs and examples,
then compose the UI. For example: "Read the Form, Field, and Button documentation,
then build an accessible website submission form using @lemuel-manske/components."

Add guidance like this to the consuming project's agent instructions:

```text
Before using @lemuel-manske/components, read its setup guide and retrieve the relevant
component APIs and examples through the configured Storybook MCP server or documentation files.
Use public package imports. Verify props and compound parts before using them.
Follow the theme, stylesheet, accessibility, and semantic token guidance.
Check the installed package version against the documentation version.
Type-check the generated UI and test its important interactions and accessible names.
```

MCP and manifest APIs are Storybook preview features. Keep addon versions aligned with
Storybook and inspect the generated manifests after upgrades.

## Access without MCP

```sh
npm run build
npm run build:docs
```

The combined static output is `website/dist`. It includes:

- `llms.txt`: an index of the exported Markdown guides and component manifests.
- `agent/docs/**/*.md`: Markdown generated from the same MDX used in Storybook.
- `agent/manifests/components.json`: generated component APIs and story examples.
- `agent/manifests/docs.json`: generated MDX documentation metadata.
- `agent/docs/version.json`: package versions and the build commit when available.
- `storybook/`: the interactive component explorer.

The Docusaurus portal is configured for `https://lemuel-manske.github.io/ui/`, with Storybook
under `/ui/storybook/`. GitHub Pages serves these files; it does not run an MCP server.
Use the live development endpoint or deploy a separate MCP service if remote tools are required.

## Preview and deployment

Run `npm run docs` for the Docusaurus development server; it prepares a snapshot of the
source guides and APIs when starting. Restart it after changing documentation sources to
refresh that snapshot. Use the complete build preview for Storybook links.

In the GitHub repository, set **Settings → Pages → Build and deployment → Source** to
**GitHub Actions**. The documentation workflow builds and deploys changes on `main` and supports
manual runs. Pull requests build the combined site through the checks workflow.

Keep the configured URL and base path in `scripts/docs-config.js` aligned with the Pages
address. Generated files stay ignored; edit the original component MDX, source types, and stories.

## Maintaining the documentation

Document each public prop's purpose, type, and default in source JSDoc. Use `@remarks` for
the type description so the generated API retains TypeScript's inferred unions, and use
`@default` for defaults. Describe inherited accessibility props at their shared declaration.
Show representative states in stories and explain compositions in MDX.

Register component-specific parts as story subcomponents using direct component imports.
Compose standalone components directly when a compound alias adds no behavior.
Declare stories with `export const` so manifest extraction can find them.
Keep examples on the public API. Build documentation in CI to catch broken MDX and extraction
failures; inspect the artifact when changing component APIs or upgrading Storybook.
Generated page templates live in `scripts/templates/`; shared paths and artifact names live
in `scripts/docs-config.js`. Keep document text in templates and file processing in scripts.
